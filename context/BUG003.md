# BUG003: Race Condition in Candidate Progress Reporting

## Analysis

A race condition exists in the `IdentifyCandidatesHandler` where thread-local increments of the completed counter and the subsequent progress report are non-atomic. When `Parallel.ForEachAsync` runs with concurrency > 1, two threads can increment the counter and then deliver their progress reports out of order, violating the monotonically-increasing invariant expected by the UI state machine and progress display.

The bug was latent in earlier versions but became reproducible under the load of US157's new per-stage progress reporting (roughly 5x more progress.Report calls per document). The test `IdentifyAsync_ConcurrentProcessing_ProgressAdvancesWithoutLostUpdates` now fails intermittently.

## Root Cause

- **IdentifyCandidatesHandler.cs, RunState.Advance (lines 94-98) and RunState.Record (lines 84-92)**: Call `Interlocked.Increment(ref _completed)` followed by a separate `progress?.Report(...)` call. The two operations are not atomic.
- **Parallel.ForEachAsync with concurrency > 1**: Thread A may increment and then be preempted before calling Report; thread B increments and delivers its Report first. The UI observes [2, 3, 4] instead of [1, 2, 3, 4].
- **CandidateRunState.Report (Presentation/Services, ~line 65-72)**: Uses last-write-wins (`Completed = progress.Completed`), so stale/out-of-order reports overwrite recent ones. The UI caption momentarily shows "2 of 5" then jumps back to "1 of 5" when the delayed report arrives.

## Affected Code

- `Cortexa-dev/desktop/collector/src/Collector.Application/Candidates/IdentifyCandidatesHandler.cs:94-104`
- `Cortexa-dev/desktop/collector/src/Collector.Presentation/Services/CandidateRunState.cs:65-72`
- `tests/Collector.Tests/Candidates/IdentifyCandidatesHandlerTests.cs:216-238` (failing test)

## Fix Options

1. **Atomic increment-and-report**: Acquire a lock before Interlocked.Increment and hold it through progress.Report.
2. **Snapshot state**: Read _completed and documentIndex atomically, then call Report outside the critical section with the snapshot.
3. **Max-seen tracking in UI**: Have CandidateRunState track `max(Completed)` instead of direct assignment, so out-of-order reports cannot regress the UI state.
