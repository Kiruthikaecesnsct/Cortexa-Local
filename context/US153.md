# US153 - Identify invention candidates from whole documents with Gemini

## What we analyzed

The Process button runs unit knowledge extraction (UnitBuilder, CodeSplitter, chunking) and has no candidate step. The earlier plan had the desktop extract knowledge only, with Cortexa finding candidates. This item changes that for the candidate pass: the desktop reads each selected file whole, asks Gemini once per file, and keeps the candidates locally. Whole-file reading avoids losing an invention that spans chunk boundaries. The limit check uses the exact CountTokens result, so an oversize file fails with counts instead of being cut.

## Affected modules and files

All paths sit under `desktop/collector`.

- `Collector.Application/Candidates` - new: whole document reader, limit check, handler, InventionCandidate, CandidateRunResult.
- `Collector.Infrastructure/Ai` - CountTokens and generate calls on the existing Gemini client factory; AiFailureKind to outcome mapping.
- `Candidates/Prompts/candidate-prompt.v1.json` and `candidate-output.schema.json` - written first, checked against current Gemini structured-output docs.
- Reused, not changed: GeminiDirectProvider, GeminiClientFactory, GeminiKeyStore, DocumentStore, PdfTextExtractor, DocxTextExtractor, FileContentGuard, TextNormalizer, AnchorLocator.
- Config: `Ai:Gemini:MaxInputTokens`, the Gemini model id, the existing per-provider concurrency setting.
- Not touched: `services/`, `contracts/`, `frontend/`, and `Knowledge/` (UnitBuilder and CodeSplitter stay).

## Assumptions

- The FileContentGuard size cap runs before the token check.
- Concurrency reuses the existing per-provider setting. No new key.
- Candidates live in memory for the session only.
- A quote the source check cannot find is marked unverified and kept.

## Open questions

1. Does the candidate pass run on every Process run, always on Gemini, or only when Gemini is the active provider? Assumed: every Process run, always Gemini.
2. One request per file, never concatenated. Assumed as written.
3. Does the FileContentGuard TooLarge cap stay before the token check? Assumed yes.

## Pre-flight

Folds applied to the story (0.5h total, RemainingWork 12.0 to 12.5, StoryPoints unchanged at 1.5):

- Prompt files `Candidates/Prompts/*.json` are embedded as EmbeddedResource in `Collector.Application.csproj`. Added to the prompt design task.
- `CandidateRunResult` gains a `Failed` outcome with a reason. It covers malformed candidate JSON, a refused or truncated Gemini response, and Permanent errors other than auth (400, 404, 413, 422). Outcome mapping: MissingApiKey to KeyMissing, QuotaExceeded to Quota, Transient to Network, Permanent auth to KeyRejected, other Permanent to Failed. Added a test case. The 0.5h went to the outcome mapping task (now 3.5h).
- FileContentGuard's 1 MiB cap covers text and code only. PDF and DOCX have no byte cap, so token count is their only limit.
- The new count-tokens port must not reuse the name ITokenCounter.
- CountTokens may not accept SystemInstruction on the Gemini Developer API. Count the system prompt as content.
