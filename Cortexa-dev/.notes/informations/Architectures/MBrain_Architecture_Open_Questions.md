# MBrain — Open Questions on Flow & Architecture

Engineering-side doubts found while reading the reference doc and scoping US122–US127. Not for Madhan's interview — these are build-order, data-layer, and spec-consistency questions that need a product/architecture call, not domain expertise. Some restate gaps the source doc already flagged (§18); others surfaced while writing the stories.

---

## 1. Restated from the source doc's own "Points to Clarify" (§18)

1. **Zone numbering vs. roadmap.** The roadmap's 3–6 month milestone says "Cognitive Zones 1–4 operational," but by the doc's own numbering Zones 1–4 are Novelty/Inventiveness/Commercial/Portfolio — while the MVP only needs Novelty, Patent Gym (Zone 5), and Governance (Zone 6). Is the roadmap wording stale, or did zone priority actually change? (This directly affects whether US124/125 are really the MVP-blocking pair I assumed.)
2. **Novelty Zone timing.** MVP scope includes the Novelty Zone; a later sprint lists "Novelty Intelligence Zone (complete specification, initial knowledge base)" as if it ships later. Which subset of Novelty ships at MVP vs. in the follow-up pass?
3. **Bypass allow-list.** The spec requires the MMIF-operational bypass (formatting, data retrieval, admin queries) to be "explicitly defined," but never enumerates the actual request types. US122/US123 can't finish the bypass logic without this list — who owns writing it?
4. **Validated Output Learning mechanics.** The doc says confirmed outputs get fed back "as a validated training signal," but also insists MBrain is explicitly *not* a fine-tuned LLM. Does "learning" mean updating structured rules/weights in the knowledge base, or something else? And how does that reconcile with the no-cross-client-training rule?
5. **Weighted rules.** Zones are described as backed by "weighted rules," but no weighting scheme or ownership of the weights is specified anywhere. Is this a real mechanism we need to design, or a looser way of saying "some rules take priority"?
6. **Knowledge Graph technology.** Still an open choice between Neo4j / Cosmos DB Gremlin / Amazon Neptune. This blocks US127's actual implementation — the client-isolation query-layer work depends on which engine we're filtering against.

## 2. Surfaced while scoping US122–US127

7. **Saga wiring specifics.** US122 inserts two new steps into job-orchestrator's saga (`mbrain.inbound`, `mbrain.validate`) bracketing scoring/harvesting/seeding — but the existing saga is a linear pipeline per engine, not a shared pre/post hook across all three. Does MBrain wrap *each* engine's call individually, or sit as one shared gate the saga routes every engine through? The doc's T-structure implies the latter; the current orchestrator code doesn't have that shape yet.
8. **Audit log store.** I chose Azure PostgreSQL (the existing `identity` DB) for the append-only `mbrain_audit_log` table, reusing the one relational store already in the stack. The doc doesn't specify a store. Is piggybacking on `identity`'s Postgres acceptable long-term, or should audit logging get its own isolated database given the 7-year retention and compliance sensitivity?
9. **SaaS vs. On-Premise zone parity.** Doc requires MBrain to "reason over an isolated, client-only Knowledge Graph" in On-Premise deployments. Nothing in the current Terraform/deployment design handles a client-hosted Knowledge Graph at all — is On-Premise deployment realistically in scope for the next 12 months, or can US127's isolation work assume SaaS-only for now and treat On-Premise as a later architectural pass?
10. **Expert Review Council workflow — permanent gate or interim scaffold?** US125 assumes seeding's Level 2 (Council approval) is a separate, not-yet-built story. Before building it, confirm the intent: is Council approval meant to stay a standing human gate indefinitely, or is it a bridge step that exists only until MBrain's own encoded judgment (from the Madhan interview) is confident enough to clear seeded concepts on its own? That changes the design — a permanent gate needs a durable Council UI; an interim one needs to be built as a bypassable step MBrain can eventually own outright, not load-bearing infrastructure. Is there an existing internal tool/process for this today (even a manual one — spreadsheet, email) to model the interim version against?
11. **Six zones, two engines.** Only Harvesting and Seeding exist today; Evaluation/Drafting/Portfolio/Commercialization (which consume Inventiveness/Commercial/Portfolio zones) don't. Confirm this means Zones 2–4 are correctly out of scope until those engines get built — i.e., no hidden dependency where Harvesting or Seeding secretly needs Inventiveness or Commercial reasoning sooner than expected.
12. **Reasoning trace format.** The doc wants reasoning traces that are both machine-auditable and human-readable for attorney review. Is one representation meant to serve both audiences, or does the attorney-facing version need separate formatting/plain-language work on top of the raw audit trace?

## 3. Scope/sequencing risk

13. The knowledge-curation workstream (interview document, separate) is the actual long pole — US123/124/125 can ship with correct schemas and dead logic without it. Worth deciding explicitly: do we ship zones with placeholder/generic reasoning as an interim state, or hold the zones un-merged until the encoded reasoning exists? The target state either way is the same — MBrain running as the standing decision layer for Harvesting/Seeding on its own, not a human reviewing each verdict — so this is purely a sequencing call: can Sprint 6 "complete" on placeholder zone logic, with the real encoded rules swapped in once the interview content lands, or does merge wait for that content outright?
