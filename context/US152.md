# US152: Entra ID sign-in for Azure DevOps

## Scope

- Adds Microsoft Entra ID sign-in to the desktop collector Remote source connect step for Azure DevOps. PAT stays as the fallback.
- Interactive sign-in uses MSAL with the WAM broker and falls back to the system browser. Device code is the last resort.
- Requests `499b84ac-1321-427f-aa17-267ca6975798/.default`. The deprecated Azure DevOps OAuth app registrations are not used.
- Org URL stays required. Out of scope: service principals, Azure CLI token reuse, SSH.
- The Entra ID methods are added next to PAT, not in place of it. The existing PAT sign-in is not removed or changed: PatAuthHandler, PatScheme and the PAT connect path must keep working, and all existing PAT tests must still pass.

## Affected files (desktop/collector/src)

- Collector.Infrastructure/Remote/AzureDevOps/*: existing clients get the Bearer token the same way the PAT does.
- Collector.Infrastructure/Remote/PatAuthHandler.cs and PatScheme.cs: pattern for the new Entra auth handler and scheme selection.
- Collector.Infrastructure/Secrets/CredentialManagerStore.cs: holds the encrypted MSAL token cache (DPAPI). Sign-out clears it.
- Collector.Application/Remote/RemoteConnectRules.cs: auth-method choice rules.
- Collector.Application/Remote/RemoteFailureMessages: clear no-access message.
- Collector.Presentation: RemoteSourceView, RemoteSourceViewModel (+ .Wizard, .Repositories partials).
- Collector.Infrastructure csproj: adds Microsoft.Identity.Client and Microsoft.Identity.Client.Broker (versions verified at implementation time). Not referenced in src today.

## Assumptions

- Client ID, tenant authority and redirect URI are config-driven. No secret is shipped in the app (public client).
- WAM needs the app redirect URI registered in the Entra app as a nativeclient/broker redirect.
- MSAL cache bytes are written only through CredentialManagerStore, never to settings or logs.

## Open questions

- Who owns the Entra app registration, and in which tenant?
- Single-tenant or multi-tenant? Single-tenant is simpler to lock down, multi-tenant fits other orgs.
- Does the Azure DevOps delegated permission need admin consent in our tenant before users can sign in?
- Is the target Azure DevOps organization Entra-backed? If it uses GitHub or Microsoft accounts only, Entra sign-in will not reach it and PAT stays the only path.
- Which client ID goes into config for dev and for Alpha's machine?

## Resolved

- Token persistence (decided 2026-10-13, see `decisions/20261013-collector-oauth-token-persistence.md`): the US152 Entra ID MSAL cache may be stored encrypted in Windows Credential Manager so sign-in survives a restart. Approved exception to US138 for OAuth tokens only. PATs and the SSH passphrase stay session-only. The US138 startup purge must skip the OAuth slots. Sign-out clears them.

## Prerequisites

- None in the backlog. The Entra app registration, tenant choice and admin consent are external prerequisites, not stories.
